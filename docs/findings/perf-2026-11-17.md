- Projects folder (read only): 42 project folders, 163 transcripts, 861.9 MB, 7 transcripts over 20 MB, largest 72.9 MB.

## Fix 1, index build in parallel (round 10 item 2)

The default `TranscriptIndex.Build` reads the files on several threads, each into a ledger of its own, then combines the ledgers in
the order the one-after-another build reads them. The one-after-another build stays as the reference (the overload with a reader).

The data moved during the day (live sessions), so the before and after numbers below were taken on the same snapshot: 862.5 MB,
27,955 messages counted once. Fresh process each time, `--repeat 1`, five runs each:

| Index build | Runs (s) | Median | Peak working set |
|---|---|---|---|
| Before (item 1 build) | 4.03, 3.66, 4.00, 3.88, 3.78 | 3.88 s | 86 to 100 MB |
| After (parallel) | 1.61, 1.54, 1.69, 1.56, 1.57 | 1.57 s | 167 to 207 MB |

Output: the test `TranscriptIndexParallelTests` compares every field of the index (sessions, totals, models in order, skipped files)
between the two builds on a fixture with copied messages, a message written twice, one message under two models, unkeyed records, a
subagent file, files created out of name order and a locked file. A mutation that drops the per-file usage rule fails the test.

Where the time goes (probe on the same folder, not committed): reading the raw bytes in parallel takes 0.03 s, decoding the lines
0.3 s, and the JSON summary of every line 0.7 to 0.9 s. The merge takes about 0.02 s. What is left is the JSON parse itself.

## Fix 2, search pre-filter for a word with an escaped character (round 10 item 2)

A word with a backslash or a quote was never pre-filtered, so every line of every transcript was parsed. Now it is looked for by its
longest run of plain characters (`RawProbe`: "C:\Windows\System32" gives "System32"). A message that holds the word also holds that
run unescaped in its raw line, so no match is lost. The test `HistorySearchRawProbeTests` checks the probe values, the path search,
and a reference that parses every line (the rule before this fix) on twelve queries over six sessions with escapes, quotes, tabs,
a newline and an emoji.

Same snapshot, the search step of the bench, two runs each, run 1 then run 2 (seconds). The search includes the untimed index build
the bench makes first, so its process peak is the index's:

| Query | Before (s) | After pre-filter (s) |
|---|---|---|
| Common word | 0.989, 0.948 | 1.501, 0.971 |
| Rare word | 0.900, 0.899 | 0.965, 0.899 |
| Windows path | 1.975, 1.983 | 0.894, 0.885 |

## Fix 3, search reads its sessions in batches on several threads (round 10 item 2)

`RunCounted` reads the newest-first sessions in batches of 32, on as many threads as there are processors. The results are then taken
one by one in the same order, so the matches, the count of unreadable sessions and the stop at 100 matches are those of the
one-by-one loop. Tests: `HistorySearchBatchTests` (a cap reached inside a batch leaves a later unreadable session uncounted; every
unreadable session is counted when all are read) and the existing search tests. A mutation that removes the stop fails two tests.

Same bench step, two runs each, after the pre-filter (seconds; the snapshot had grown to 863.4 MB, so the numbers are not comparable
to the table above line for line; see the final table):

| Query | After pre-filter (s) | After batches (s) |
|---|---|---|
| Common word | 1.501, 0.971 | 0.882, 0.505 |
| Rare word | 0.965, 0.899 | 0.355, 0.341 |
| Windows path | 0.894, 0.885 | 0.369, 0.354 |

## Fix 4, the index keeps each transcript's read between starts (round 10 item 2)

`TranscriptIndex.Build(root, cachePath)` keeps, per transcript, its length and write time, its summary and its counted messages. A
transcript with the same length and write time as its entry is not read again. The file names the build of the reader that wrote it
(the module id, which changes with the code), so a cache from another build is not used. The app keeps the cache beside its state
file: `%LOCALAPPDATA%\OpenTail.Bullshark\cache\transcript-index.json` for the owner, about 5 MB for 163 transcripts.

Verification on the owner's folder (bench step `verify`, scratch cache, prints hashes only): the reader after one transcript, the
parallel build, the cache as written and the cache as read give the same index, the same hash, 163 sessions, 28,025 messages counted
once, nothing skipped. Output: `identical: True`.

Tests: `TranscriptIndexCacheTests` (nine): a cold build writes the cache and gives the reader's index; a warm build does too; a
transcript changed in content only is served from the cache (the stated rule); an appended transcript is read again; a removed one
leaves the cache; a damaged cache is ignored and written again; another reader's cache is ignored; an unchanged locked transcript
is served from the cache; a changed locked transcript is left out, as the reader leaves it. Mutations of the length and write time
check, and of the reader check, each fail tests.

Same bench, fresh process each, same folder (seconds):

| Path | Runs (s) | Median | Peak working set |
|---|---|---|---|
| Index build, no cache (after fix 1) | 1.84, 1.54, 1.51 (earlier 5 runs: 1.54 to 1.69) | about 1.6 | 177 to 277 MB |
| Index build, warm cache | 0.175, 0.176, 0.181, 0.175, 0.179 | 0.18 | 63 to 64 MB |
| History path (index and tails), no cache | 1.69, 1.80, 1.81 | 1.80 | 178 to 254 MB |
| History path (index and tails), warm cache | 0.33, 0.25, 0.26 | 0.26 | 66 to 74 MB |

The first build with an empty cache takes about the same as one without (1.83 s): the cache is written after the read. The history
path is what the window waits for before its rail is filled (item 3). The window itself was not run, because its startup pass calls
the claude CLI (`agents`, `daemon status`), which the round's rules do not allow. WPF start and the rail drawing are not in these numbers.

Still over 1 s: the first read with no cache (about 1.6 s on this data, 16 threads). It is the JSON parse of about 300,000 lines.
Reading the bytes and decoding the lines take about 0.3 s on 16 threads, so a parser that reads UTF-8 bytes without the DOM is the next
step. It is not done in this round: it changes the code that every number depends on, and the cache already makes a start cheap.
