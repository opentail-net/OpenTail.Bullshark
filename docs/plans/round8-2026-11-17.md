| Member | Promise |
|---|---|

## Decisions made while building

- **B1.1 (item 1).** `IdleListing` had merged working and blocked into one `stale`, so the policy could not tell them apart. `AgentInfo` gets an optional trailing `ListedState` (public signatures unchanged): the state the listing printed, set only on stale rows. The policy reads it.
- **B1.2 (item 1).** A stale working session goes through the rules for a lost one (stop guard, limit, restart loop). A stale blocked session gets one `Blocked` alert with the detail "was waiting for input when the background daemon stopped; open its tab to resume it" and is not resumed. It is also not resumed when its row later drops from the listing, while its alert stands (the roster drop would otherwise look like "gone" and resume it).
- **B1.3 (item 1).** The stale-blocked alert clears when the session is listed live again (not stale), so a later stale spell alerts again. An alert that only exists in `LastAlert` is invisible to the owner, so `AttentionList` shows a stale-blocked session as a `Blocked` item while its alert stands. Alerts reach the owner through that list (name-based announcement), not through the action count.
- **B1.4 (item 1).** Adoption skips stale rows, as the plan says. A role whose record is lost while a dead row still lists its name starts a new session. Whether `claude --bg` accepts a name that a dead row still holds is not verified: check on the owner's machine before relying on it.
- **B1.5 (item 1).** Restarts of a stale working session are counted per resume, so while the roster keeps the dead row the session is resumed on each pass until the restart limit (3 an hour), then a restart-loop alert stands. Bounded, not a loop.
- **B1.6 (item 1).** Mutation check: the stale-working branch returning `[]` fails `AStaleWorkingSessionIsLostAndResumedUnderTheSameId` and `ADeadDaemonResumesAStaleWorkingSessionAsALostOne`; restored, identical hash.
- **B1.7 (item 1).** Revised two round 7 tests that asserted the old rule: the stale blocked pass now alerts once, and the stale-then-back-blocked test expects the stale alert on the first pass (the return to blocked is item 2's change).
- **B2.1 (item 2).** The supervisor records `AgentInfo.ObservedState`: the listed state of a stale row, otherwise the listed state. "stale" is for display and decisions only. Only Core reads `LastState`, so nothing else changes. The state events now read `blocked -> ...` where they read `-> stale` before.
- **B2.2 (item 2).** Sequence blocked, stale, blocked: the first entry is announced (sound and flash) as before. The stale alert is one policy action, and the Needs-you item for the session stays the same session name, so it is not announced again, and the return to blocked adds no alert. The owner hears no sound when the daemon stops a session that was already waiting; the row text changes to the stale detail. Open for the owner: a sound for that case, if wanted.
- **B2.3 (item 2).** Mutation check: recording `EffectiveState` again (stale) fails `ABlockedSessionThatGoesStaleAndBackBlockedIsAnnouncedOnce`, `AStaleWorkingSessionIsRecordedAsWorkingNotAsStale` and `ADeadDaemonAlertsOnceForAStaleBlockedSessionAndResumesNothing`; restored, identical hash.
- **B3.1 (item 3).** The hold is a Core class, `RespawnHold` (20 seconds after the respawn ends, clock injected). The runner drops a Start or Resume decision while the hold is on; it still reads the listing, adopts a live session (no process starts), and carries alerts. A dropped decision writes nothing, and the next pass that is not held decides again.
- **B3.2 (item 3).** The dialog does not promise what the CLI does to stopped sessions: `claude respawn --help` says only "Restart a background session (or all of them) so it picks up the current Claude binary". The text says Bullshark does not restart a stopped session and that whether `claude respawn --all` does is not checked. "Blocked sessions lose the prompt they are waiting on" is the planner's statement; it is not captured on this machine, and the text states it as the plan asks.
- **B3.3 (item 3).** The reviewer's "pause the timer" is not done: with the hold, a timer pass during a respawn only reads and shows, so the timer keeps running. Owner-started resumes (History) and closes are not pass decisions and are not held.
- **B3.4 (item 3).** Mutation check: removing the runner's skip fails `DuringTheHoldAMissingSessionIsNotResumed` and `DuringTheHoldAFirstStartIsNotCarriedOut`; restored, identical hash.
- **B4.1 (item 4).** Built: an adoption carries the session's listed `startedAt` (`SupervisorAction.Adopt.StartedAt`, an optional trailing parameter; null when the listing has none, then "now"). A lost record, or a failed-start record whose session was then found listed, no longer starts the clock at the adoption.
- **B4.2 (item 4).** Not built: carrying an earlier start over to a new record with a session id, and a `FirstStartedAt` field. No path replaces a record that holds a session id: `Start` and `Adopt` run only when the record is absent or has no session id; `Resume` copies the record, so `StartedAt` is kept; `RetryButton` removes only records without a session id; closing a session removes its spec and record; a new run gets new names from its run id, with its own limit. Old records load unchanged (no field added).
- **B4.3 (item 4), open for the owner.** Closing a session (`CloseSessionAndTabAsync`) removes its spec from the run and its record, so `RunBudget.ElapsedOf` and `RunSpend` stop counting it: the run's clock starts from the next earliest session and the spent output tokens of that session drop out. The session has already spent them. A limit is therefore reset by closing the earliest session. Not changed here (it is the owner's action, and outside this item); decide whether a closed session should keep counting.
- **B5.1 (item 5).** The header counts the rows listed under it, the daemon note included (`AttentionList.NeedsYouRowCount`, which counts a session only when it has a record). So a note alone reads "Needs you (1)" over its one row, and a session plus the note reads (2). The status bar line "N sessions need you" still counts sessions only; it is a separate element, and I left it. Before the change the code read `_attention` for the header (`SessionWindow.Attention.cs` line 48) and the rail showed the section with `_attention.Count == 0` (`SessionWindow.Rail.cs` line 302), so the header said (1) over two rows or (0) over one.
- **B5.2 (item 5).** Screenshot: `scripts/Test-NewScreens.ps1` run on the branch, scratch folder under `scratchpad\r8-ui\item5-screens`; `daemon-down-dark.png` shows "Needs you (2)": the daemon note and the stopped coder, not listed. The planner and the working coder are not in the group: their rows are stale and show "not running (daemon idle)" with no reason.
- **B6.1 (item 6).** `GitChanges.FolderOf` chooses only folders that exist, for all three candidates, as its contract says. The transcript's folder is normalised first; a candidate the normaliser throws on is skipped, and the call never throws. The listing's and the spec's folders are used as given (no normalising), so a Unix-style path is not turned into a Windows path here.
- **B6.2 (item 6).** Existing tests that used non-existent `C:\...` folders for `FolderOf` were revised to real temp folders (`WorktreeFolderTests`, `GitChangesTests`): under the contract they could not pass otherwise.
- **B6.3 (item 6).** A merge check that returns `Problem` leaves the coder out of the started set, so the next pass checks it again while it stays `done`. A persistent problem is therefore one check per pass (every 15 s) for that coder, not a single attempt. I took that over a backoff: a missing folder fails before git runs, and a git timeout is the owner's problem to see in the report. Open for the owner if git timeouts get expensive.
- **B6.4 (item 6).** Residual: `FolderKey.Normalise` still maps a path it can parse (for example `/home/x`) to a Windows path; with the existence check, that path is used only if it exists. Not changed.
- **B6.5 (item 6).** Mutation check: narrowing the normaliser's catch fails `AFolderThatTheNormaliserRejectsIsSkippedAndNothingThrows`; restored, identical hash. The window's merge clearing is one line over the tested `MergeCheck.ShouldRecheck`; no window test exists for it.
- **B7.1 (item 7).** `DaemonStatus.Parse` keeps `Version` only when the state is Running. The window's drift check now calls the new `VersionDrift.OfStatus(status, cli)`, which needs a running daemon; `VersionDrift.Of(string, string)` is unchanged, so public signatures hold. A new name rather than an overload, since an overload makes a `null` first argument ambiguous.
- **B7.2 (item 7).** `Pid` and `Uptime` are still read from any text. Nothing reads them in the window or the policy (checked), so they are left as they were.
- **B8.1 (item 8).** The reader records, for each relative write, the cwd of the record that carries the write (that record's own cwd if it names one, else the last one named). The cache keeps the newest folder per path, and `FileOverlap.Find` resolves a relative path against that folder, then the session's latest folder, then the run's. The `Files` list the Changes tab shows is unchanged.
- **B8.2 (item 8), residual.** A relative path written from two different folders keeps only its latest folder, as it already keeps only its latest write time. An earlier write of the same relative text from the other folder is then resolved against the later folder. Not built: it would need one entry per (path, folder) through the cache and the overlap.
- **B8.3 (item 8), not in this item.** The reviewer's second point, that a session which `cd`s into a subfolder shows that subfolder as its Changes and merge folder, is unchanged: the round 7 choice of the latest cwd still stands. Open for the owner.
- **B8.4 (item 8).** Tests: `ARelativeWriteIsTakenFromTheFolderItWasWrittenIn` (the overlap uses the write's folder) and `TheCacheKeepsTheFolderOfEachRelativeWriteFromItsOwnRecord` (reader and cache, appended read included). No mutation check: item 8 is not one of the money items 1-4.
- **B9.1 (item 9).** An object or array in `waitingFor` or `status` is read as text: an object's `kind`, else its `text`, else its `message`, else its first string value; an array's first text item. A shape with no text gives no reason and no state (`EffectiveState` then falls to "unknown"). The raw JSON is never shown.
- **B9.2 (item 9).** The round 7 test `AWaitingReasonAsAnObjectIsItsRawJson` asserted the raw JSON this item forbids; it is now `AWaitingReasonAsAnObjectShowsItsKindNotItsJson` (expects "dialog"). A `status` object with a `kind` is now the state text, which the policy then reads like any other status; before, the policy left the raw JSON alone.
- **B10.1 (item 10).** The fit moved to Core as `EffortReport.FitPaths`: the first `MaxFittedPaths` (200) paths are trimmed by `FitPath`, with the suffix measured and never trimmed; the rest are shown whole, and their tooltip already holds the full path. The window measures only the text of those it fits.

The reviewer's binary search of the boundary is not built: `FitPath` already tries the folder boundaries from the longest suffix, and the cap bounds the work to 200 paths.
- **B10.3 (item 10).** Tests: `FitPathsTrimsEachPathWithItsSuffixInThePanelsOrder` and `PastTheCapThePathsAreShownWholeAndAreNotMeasured`. The window part (timer and measuring) is checked on the effort screens of the final screenshot run, not by a unit test.
