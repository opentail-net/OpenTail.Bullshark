## Decisions made while building

### Item 1 (denied state or run file)
- Mechanism checked by a probe in a scratch project (not committed). `File.Exists` is false only when the parent folder's DACL gives the current user no entry: a protected folder with no entry gave `File.Exists` false and an open that throws `UnauthorizedAccessException`. When only the file's own DACL denies reading, `File.Exists` is true and the old read threw a raw `UnauthorizedAccessException`, not `StoreUnreadableException`. So "reads as empty" holds for a folder the user cannot open; for a denied file the store already refused to write, but the exception type broke the contract. Both cases now throw `StoreUnreadableException`.
- Changed: `RunStore.Read` and `StateStore.Read` open the file directly. Missing is empty. Any other read failure, and a JSON parse failure, throws `StoreUnreadableException`, so `Update` and `Save` never write.
- Changed: `TabOrder.Load` logs an unreadable file (the old code logged nothing for a folder the user cannot open). `TabOrder.Save` leaves a file that is there but cannot be opened as it is, and logs the save (the old save replaced it when the folder allowed writing).
- Changed: `EventLog.Read` opens the file directly. An unreadable log is an error, which the timeline already shows as "cannot be read". A missing rotated file is still skipped.
- Already correct, unchanged: `SessionLibrary.Read`, `PatternStore.Read` (both open directly and catch the missing-file exceptions), `UiSettingsFile.ReadRoot` (open directly; a failed `Set` writes nothing).
- Not changed, and why: `ClaudeTrust.Read` reads Claude's own `.claude.json` and writes nothing. A folder the user cannot open gives "nothing trusted, no problem", which is safe (nothing starts) but the message is wrong. It is not a store, so it is recorded only. `InstructionFiles.Read` returns empty when `File.Exists` is false, so the instructions dialog shows an unreadable file as empty; its `Save` was not checked in this item. `EventLog.Write` still moves `events.jsonl` over `events.1.jsonl` at the size limit even if the older file cannot be read (history only, rare).
- Test tooling: the `Unreadable` helper in `tests/.../Support`. A first version restored a folder by calling `SetAccessControl` on an object it had only read. .NET does not write back an unmodified object, so the folder stayed locked. The red run left four test folders in `%TEMP%` locked to SYSTEM; I regranted my access to exactly those four and removed them. The helper now restores from the SDDL string saved before the change, and the temp folders are clean after the run.
- Tests: 14 new, 641 in total. Seven fail on the old code (the folder and file cases in RunStore, StateStore, TabOrder and EventLog). The exclusive-open, non-JSON and missing-file tests pass before and after, as regression guards.

### Item 2 (one filter for expected failures)
- `StoreErrors.IsExpected(ex)` is in `Core/Supervisor/FileLock.cs`, beside `StoreUnreadableException`. It is `StoreUnreadableException`, `TimeoutException`, `IOException` (which covers the missing-file exceptions) and `UnauthorizedAccessException`. Two tests in `StoreErrorsTests`.
- Every store catch in the App now uses it: `SessionWindow.Tabs.cs` (the restore after a failed close), `SessionWindow.xaml.cs` (the run write, the retry of failed starts, and the two load helpers), `SessionWindow.Schedule.cs`, `SessionWindow.Library.cs` (2), `SessionWindow.Resume.cs` (2), `SetupView.xaml.cs` (4), `SessionWindow.Timeline.cs`.
- The plan's list was partly off: `SessionWindow.Schedule.cs` had a one-type catch (`StoreUnreadableException`), not the three-type list, so it was widened. `SessionWindow.Timeline.cs` caught only `IOException` and `UnauthorizedAccessException`; it now also catches the store and lock errors, since `EventLog.Read` takes the file lock and a timeout there left the timeline silently empty.
- `LoadRecords` and `LoadRuns` (the window's read helpers) now return a lock timeout as the store problem instead of letting it escape. The close path reads the runs and records before its own try block, so a timeout there would have been an unreported click failure.
- `SetupView.SuggestedFolders` keeps `ArgumentException` and `NotSupportedException` next to the helper: they are path errors from the state file's folder, not store errors.
- Not changed, IO-only and not on a store path: `InstructionsDialog.cs:151`, `RailTheme.cs:88` (its `UiFile.Set` already catches internally), `SessionWindow.Overlap.cs:46` (transcript read), `SessionWindow.Resume.cs:267` (summary file), `TranscriptView.cs:538`, `576`, `597`.
- Not changed, by design: `UiSettingsFile.Set` (zoom, theme) and `TabOrder.Save` (tab order) log a failed save and do not show it in the status line. These are preferences, and their own docs say so. The contract's status-line rule is applied to the owner's store writes. The owner can ask for a status line on them.
- The App has no test project. The change there is the filter in each catch; its logic is tested by `StoreErrorsTests`, and the screens are checked in item 5.
- Tests: 643 in total (2 new), all green. Build: one warning, the same as the baseline (`MainWindow.xaml.cs(23,33)`).

### Item 3 (hook commands: `NAME=value` and shell built-ins)
- `CheckHook` skips the words that are `NAME=value` before the program (a name of letters, digits and underscores, not starting with a digit). The program is the first other word, and it is checked as before. `IsAssignment` and `ShellBuiltIns` are in `Health/SetupCheck.cs`.
- A shell built-in is matched on the program word, ignoring case, so `ECHO` counts (cmd does not mind case). The list is the plan's list. A built-in is Ok with "shell built-in; not checked: <name>", the same state the round-3 variable case uses.
- Decided, the plan did not say: a hook that is only assignments (`FOO=1`) is a problem ("the hook sets variables and names no program"), because it runs nothing.
- Decided: the rule covers hooks only. An MCP server's command is started without a shell, so `NAME=value` there is not a shell assignment, and its check is unchanged.
- Not changed, recorded for the owner: a command chain (`cd sub && node x.js`) is judged by its first program only, as before. Here the first word is a built-in, so the whole chain is "not checked", including the `node`. A full shell parser was not in scope.
- Tests: 17 new (660 in total), all green. 16 fail on the old code: the twelve built-in cases and four of the five new facts. `1x=2 arg` (a word with `=` that is not a name, so a program) passes before and after as a guard.

### Item 4 (host argument parsing)
- The parse moved to Core: `Core/Reports/HostCommand.cs` (`HostCommand.Parse`). The host is an exe project that the test project cannot reference, so the parse could not be tested where it was. `Program.cs` now only calls it and runs the report.
- Rule: the folder is the argument straight after the first `--projects`. It is a problem when there is none, when it is blank, or when it starts with `--`. A problem prints the message and the usage, and exits 2 before any transcript is read. Before, `--projects` with nothing after it silently used the default folder, and `--projects --cache-report` read `--cache-report` as the folder name.
- Kept as before, not in the plan: `--usage-report` wins when both reports are asked for; unknown arguments are ignored; only a `--` prefix counts as a flag, so a single-dash folder is still a folder.
- Checked on the built exe: `--usage-report --projects --cache-report` and `--cache-report --projects` each print the message and exit 2. `--usage-report --projects <empty scratch folder>` exits 0 with zero files. No owner transcript was read.
- Tests: 11 new `HostCommandTests` (671 in total), all green.

### Item 5, part 1: test options (no click, no session)
- Probe (scratch, not committed): setting `USERPROFILE` in the child process does not move `Environment.GetFolderPath(UserProfile)`, which .NET reads from the profile, not the variable. So the window cannot be pointed at a scratch `.claude` by environment. The option is needed.
- `--claude-home <folder>` (`LaunchOptions.ClaudeHome`): the transcripts (`<folder>\projects`) and the archive (`<folder>\bullshark-archive`) are read from there. The App reads them through `LaunchOptions.ProjectsRoot` and `ArchiveRoot` at six places: the history index, the Changes transcript read, the session open, and the three Storage calls (archive, restore and the project sizes). Without the option the paths are the owner's, as before.
- `--open-tab storage|timeline|changes:<session name>` (`TestScreenRequest.Parse` in `Core/Ui/TestScreens.cs`): opens the screen after the first pass, with no click. A changes request names a run record; a name with no record opens nothing.
- Not redirected, read only, and not on any screen of the plan: the trust file (`~/.claude.json`) and the setup check's settings. The instructions dialog is not opened by a test option.
- Tests: 17 new in `TestScreensTests` (688 in total), all green.
