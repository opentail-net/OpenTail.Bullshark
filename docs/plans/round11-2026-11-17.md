## Decisions made while building

- Item 1: the key is a fresh stat (`FileInfo.Refresh`) taken before the read, in `ReadOne`, and compared again in `FromCache`. A stat
  that fails is not a cache hit, and the read reports the error as it does for any file. The window is 2 minutes, measured against the
  fresh write time and the start of the build. Tests use file times, not an injected clock: `Core` has no `InternalsVisibleTo` and the
  fixture files are written an hour old, so the cache tests keep their meaning. Not covered: a writer that keeps its handle open can
  leave the directory entry's length and write time behind for longer than 2 minutes, and the rule cannot see that. Taking the length
  from an open handle was not adopted: it opens every transcript on each start, with a sharing mode the writer may refuse.
- Item 2, reproduced on the code before the item: `Load` threw NullReferenceException for `"files": null` and for `"path": null` (two
  tests fail on the old filter, and pass on the new code); `Save` let an ArgumentException out (a path with a null character), which
  the IO filter did not catch. Logging: `Build(root, cache, log)` takes an optional `Action<string>`, the `EventLog` pattern, and the
  App passes `AppLog.Write`, so the lines land in `logs\app.log`. A missing cache file is not logged; a damaged one is.
- Item 2, NOT reproduced: the review's lone-surrogate example for `Save`. The reader refuses a lone surrogate escape (a high one
  `\ud800` and a low one `\udc00` both throw InvalidOperationException in `JsonDocument.GetString`), so no string of that kind reaches
  `Save`. Test fixtures with either failed in the reader, not in the save, and were dropped. The save tests use a read-only cache file
  (the move fails, the old cache stays), a cache folder in the way, and the null-character path.
- Item 2, found and NOT changed (outside the plan, pre-existing, for the owner): one transcript with a lone surrogate escape makes the
  reader throw, and `Combine` rethrows every non-IO error (the designed rule, judged correct in the review), so the whole history load
  fails for that one file. The same happens with the one-after-another reader. Options for the owner: skip a transcript that throws a
  parse error as an unreadable one, or keep failing loudly.
- Item 3: `Save` serializes to a string, then `FileLock.Hold(path)` (the ten-second wait; a timeout is logged and nothing is saved) and
  `FileLock.WriteAtomic`, which writes a unique `<cache>.<guid>.tmp` and moves it over the cache, and deletes that temporary file on
  any failure. The helper `DeleteQuietly` is gone: nothing else needed it. The sweep runs at the start of each `Load`, before the read.
- Item 3, narrower than the plan's words: the sweep deletes only `transcript-index.json.*.tmp` older than 10 minutes, not every `*.tmp`
  in the cache folder. The folder is the state folder's `cache` subfolder, and another store's temporary file there is not this cache's
  to delete. Its own names are the ones `WriteAtomic` makes, so every leftover of this cache is still swept.
- Item 3 tests: a stale temp is removed while a young one and another store's file stay; a second save leaves one file; four builds
  that all save at once (the lock takes them one at a time) leave one valid file. The ten-second lock wait is not timed in a test;
  `FileLock` has its own tests.
- Item 4, degree: `MaxDegreeOfParallelism = Math.Max(1, Environment.ProcessorCount - 1)`, not the plan's bare `Environment.ProcessorCount`.
  The review's stated defect is that a search takes every core beside the UI, which `ProcessorCount` still does; the review's fix says
  minus one. One helper (`TranscriptIndex.ReadOptions`) serves the index and the search, with the token passed on.
- Item 4, batch: the stop at 100 was already checked after each result, before the next batch starts, so that part of the plan was in
  place. The defect was the reads past the stop inside a batch of 32. A batch is now no larger than the matches still needed, which
  makes those reads fewer as the cap nears; results are unchanged (the existing cap and unreadable-count tests still hold).
- Item 4, tests: a session-counting test shows the reads stop at 100 (128 before). Cancelling at the tenth session leaves fewer than
  one batch read (32 before), and a search cancelled before it starts reads nothing (32 before). The degree is checked by calling the
  helper through reflection (it is internal). A timing test of concurrency was tried and dropped: the old search reached 14 at once on this
  16-core machine, so it could not show the limit of 15.
- Item 5: `Records` is carried now (`SummaryDto.Records`, JSON `records`, set in `EntryOf`, passed in `Restore`). Every other
  `TranscriptSummary` field that `DigestOf` reads is carried too. The allow-list, with the reason for each: `UsageByModel` (the index sets
  it from the restored ledger), `TotalUsage` (computed from it), `FileLastWrites`, `LatestCwd`, `FileFolders` (`DigestOf` does not read
  them). Older cache files are not used after this change: the reader id is the module id, and that changes with the code.
- Item 5, digest: `SessionDigest` properties are in three lists. From the file path: `SessionId`, `FilePath`, `ProjectFolder`,
  `IsSubagent`. From the summary: the other 20 that `DigestOf` sets (`Usage` comes from `TotalUsage`). Computed: `Title`, and `Span`,
  which is a public computed property too and was not named in the plan.
- Item 5, tests: the two list tests compare the public properties by reflection with the lists, exactly, and name any property in neither
  list. The round trip sets every carried field to a non-default value (timestamps with an offset, a two-item dictionary and list),
  passes it through `EntryOf`, JSON and `Restore` (reflection, the type is internal), and compares each field. Its message list is empty,
  so the ledger part of `Restore` is not covered by it; the index cache tests cover that.
- Item 5, mutation check (not committed): `Compactions` removed from `Restore` made the round trip fail ("Compactions was 2 and is 0").
  The two list tests still passed: they check names, not values. The line was put back, and the solution was built and tested again.
