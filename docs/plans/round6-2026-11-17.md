## Decisions made while building

- **Item 1.** Re-read: the defect is at `SessionWindow.xaml.cs` (the budgets were set after `RunPassAndReadAsync`). Fixed in the read step: `ReadForPassAsync` computes the budgets (`BudgetsOf`) from the records and transcript paths it has, `PassAndRefreshAsync` sets `_runner.Budgets` before the pass, and the after-pass `ReadClashes` still draws the clashes and sets the budgets for the next pass. The computation moved into Core as `RunBudget.ForRuns`. The window's ordering has no unit test (the App has no test project); the Core test shows a run at its limit gets no start or resume from a first pass. That test cannot fail on the old code, because it needs `ForRuns`, and the old runner already honoured `Budgets`.
- **Item 2.** Re-read: `SupervisorPolicy.cs` (guard) and `SupervisorRunner.cs` (state step) both confirmed. Fixed two ways. The guard reads `LastState` when the record has one, and falls back to the stop/failed alert only for a record with no listed state (a record from before the state was kept). The runner clears a `Stopped:`/`Failed:` last alert on a pass that lists the session in any other state (`done` and `working` included). Tests: revived, then lost, is resumed; a stale stop alert with a listed `working` state is resumed (both fail on the old code, checked by reverting the two files once); a record with no listed state and a stop alert is still not resumed (passes on both, a regression guard).
- **Item 3.** Re-read: `RunBudget.ElapsedOf` (lines 73-79) counted from `StartAt` with no check for a session start, confirmed. Fixed: `RunSpend.ElapsedOf(run, records, now)` counts from the earliest `StartedAt` among the run's records that have a session id; no such record gives 0, and a run still waiting for its start time gives 0. A record with an empty session id (a failed start) does not start the clock. `RunSpend.Of` uses this overload. The old `ElapsedOf(run, now)` keeps its rule, because it has no records to see starts in and its public signature must keep working; its summary says so. The existing scheduled-run test now gives its session a start at the due time (same numbers under the new rule). Three new tests fail under the old rule, checked by compiling against HEAD's `RunBudget.cs` with a forwarding shim inside `RunSpend` (the real HEAD file cannot take the new overload).
- **Item 4.** Re-read: `SupervisorRunner` (Carry, alert case) overwrote `LastAlert` for `LimitNear` and `LimitReached`, confirmed. Fixed: a limit notice now sets only `LimitLevel` (which already held the level the owner was told, and `LimitItem` reads it), so `LastAlert` keeps a restart-loop, stopped or failed alert. The notice's text is still written to the log and the event (`Emit`), which is where the owner's record of it is. Old records load unchanged. One existing test changed its expectation: the stop-then-near-limit test had asserted that the limit notice replaced the stop; it now asserts the stop stays and the level is `near`. Two tests fail on the old runner (checked by reverting `SupervisorRunner.cs` to HEAD once).
- **Item 5.** Re-read: `AttentionList.LimitItem` had no liveness check, and `Decide` lowered the level only when a budget existed (so a removed limit kept `reached`); both confirmed. Fixed: (a) the item shows only while the session is listed and not `done` (a `blocked`, `stopped` or `failed` session takes its own reason first, as before); (b) a session with no budget at all (the run has no limit, or is gone from runs.json) gets its level cleared; (c) a level above the run's current one is lowered on any session that holds it, lead or not, so a non-lead that held `reached` does not keep showing it; (d) the told level is the highest over the run's records (`RunBudget.ToldLevel`, set by `ForSessions`), so a change of lead does not repeat a notice. "Wanted spec": the attention rule does not read runs.json; a session that leaves its run is forgotten (`SessionWindow.Tabs.cs`: `WithoutSession` and `Forget`), so a record that exists is a wanted one. Six tests, each failing on HEAD's Core files (checked once by reverting the three Core files).
