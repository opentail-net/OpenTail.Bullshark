## Items, Coder A (Core)

- [ ] **A1. One shared line helper, and a bad line is skipped everywhere.** New `internal static class TranscriptJson` in `Core/Activity`
  with: `TryParse(string line, out JsonDocument doc)` (false for blank, invalid JSON, or a leading BOM is stripped first), `Str(element,
  name)`, `Long(element, name)`, `Time(element, name)` (the timestamp rule `TranscriptReader` uses today, `AssumeUniversal`), and a
  `TryRead(Action)` style guard or equivalent so that an `InvalidOperationException` or `JsonException` raised while reading one line's
  values (a lone surrogate escape, `\ud800`, throws `InvalidOperationException` in `GetString`) skips that line. Move the readers listed
  in the contracts table onto it, removing their private `Str`/`Num`/`ReadLong`/timestamp copies.
  *Why:* the owner wants one broken transcript line to cost that line only. Today each reader has its own copy of these helpers, so the
  rule would otherwise be written nine times and drift (it already has: `TranscriptPager.cs:225` keeps a leading BOM on line 1, the
  others strip it).
  Tests: for each reader, a fixture with a good line, a line with `"text":"a\ud800b"` in a field the reader reads, and another good
  line gives the same output as the fixture without the bad line. A BOM test for the pager. Existing tests unchanged.
- [ ] **A2. A transcript that still fails is left out, not fatal.** In `TranscriptIndex.Combine` (and the one-after-another overload),
  a file whose read threw a non-IO, non-cancellation exception is added to the skipped list, and the build goes on.
  *Why:* the per-line rule covers the case we know; this covers the case we don't, so the history rail never goes empty because of one
  file. Cancellation must still stop the build. Test: an injected reader that throws `InvalidOperationException` for one of three files
  gives an index of the other two with that file skipped; a cancelled build still throws.
- [ ] **A3. The writes cache matches the whole-file read.** A test that `SessionWritesCache.Read(id, path)` gives the same `Files` (in
  order) and `Folder` as `TranscriptWrites.Facts` on fixtures with relative and absolute writes, several `cwd` changes, and a file
  written twice. If they differ, make the cache match `Facts` and say so in the report.
  *Why:* Coder B moves the merge check and the Changes tab from the whole-file read to this cache (B3); this proves the swap shows the same
  files and folder.
- [ ] **A4. Process reads are bounded.** In `Core/Claude/CliRunner.cs` (around lines 62-94), after the process exits or is killed, wait
  for stdout and stderr with a timeout (as `Core/Git/GitRunner.cs:79-83` does); on the timeout, return what was read so far with
  `TimedOut: true`.
  *Why:* a child process that inherits the pipe can keep the read open after `claude` exits, and then the pass never finishes. Not seen
  in practice; the fix is cheap and copies a pattern that already exists. Test: a fake process whose output never closes returns within
  the timeout (use whatever seam `GitRunner`'s tests use; if `CliRunner` has none, record that and test only what can be tested).
- [ ] **A5. The supervisor reads fewer logs.** `Core/Supervisor/SupervisorLoop.cs:46-64` runs `claude logs` for every record on every
  15-second pass, including done and stopped sessions, only to look for the login-expiry line. Read logs only for records whose session
  is in `agents` with a live state (not `done`, `stopped`, `failed`; use the state helper the code already has), stop at the first
  session that shows the expiry line, and write the alert at most once per hour (an injected clock, or the existing testable clock).
  *Why:* the login is the account's, not the session's, so one live session tells us; ten records today means ten CLI launches every pass.
  Tests: done/stopped records are not read; the alert is written once within an hour and again after it.
- [ ] **A6. Round 10 leftovers.** (a) In `TranscriptIndex.Combine`, drop each file's own ledger once it is merged (review R6: memory
  peak). (b) Try parsing the cold index from UTF-8 bytes instead of decoded strings (`JsonDocument.Parse(ReadOnlyMemory<byte>)` per
  line). Keep (b) only if the bench (`tools/OpenTail.Bullshark.Bench`, Release, the index step, fresh process, median of 3) is at least
  15% faster with identical output (the existing `verify` hash); otherwise revert it and record the numbers.
  *Why:* the cold read is 1.6 s on the owner's data, over the 1 s line from round 10; the probe put 0.3 s in decoding.
  The bench may read the owner's `~/.claude/projects` read-only for timing; record numbers and sizes only, never names.

## Items, Coder B (App)

- [ ] **B1. A transcript that fails is skipped per session, not per pass.** `SessionWindow.Overlap.cs:47` and `SessionWindow.xaml.cs:61`
  catch only `IOException`/`UnauthorizedAccessException`. Catch any exception except `OperationCanceledException` per session, log it,
  and go on with the others.
  *Why:* today one unreadable transcript makes every 15-second pass fail, so nothing is started, resumed or alerted (the same owner
  decision as A1 and A2, on the pass side).
- [ ] **B2. No unobserved exceptions.** `SessionWindow.Merge.cs`: in `CheckMergeAsync` the transcript and spec reads (around lines
  50-52) run before the `try`, and the task is started with `_ =` (line 33), so a failure there is lost and the coder is never checked
  again. Move them inside the `try`, log, and remove the session from `_mergeStarted` so the next pass retries.
  `SessionWindow.Changes.cs:47`: wrap the reads in `ShowChangesAsync` and show the message in the Changes view. `SessionWindow.Tabs.cs`
  (around line 259): the close path's catch misses `InvalidOperationException`; widen it the same way (not cancellation) and keep the
  status message.
  *Why:* each of these fails silently today: a merge check that never runs, a Changes tab that stays on its old view, a close that does
  nothing.
- [ ] **B3. The merge check and the Changes tab use the writes cache.** Replace `TranscriptWrites.Facts(...)` in `Merge.cs` and
  `Changes.cs` with `_writesCache.Read(sessionId, path)` (path from `_transcriptPaths`, else `TranscriptReader.FindTranscript`), using
  its `Files` and `Folder`. Keep the "no transcript" and "cannot be read" messages.
  *Why:* the merge check re-reads a whole transcript every pass while a check reports a problem, and the cache already holds the same
  facts read incrementally. Coder A's A3 test proves they match.
- [ ] **B4. The pass hands the rail what it already read.** `RefreshRail` (`SessionWindow.Rail.cs:247`) reads runs (line 272) and the
  library under `FileLock` on the UI thread, every pass. Give it an optional `runs` parameter, pass the runs the pass read off-thread
  (`PassReads`, see `xaml.cs` around line 293), and keep the read for the other callers. Do the same for `Specs` in `Merge.cs`/`Changes.cs`
  if the pass already holds them.
  *Why:* a lock held by another process freezes the window for up to 10 s per read.
- [ ] **B5. Diffs draw without a brush per line.** `RailTheme.cs:65` `RailPalette.Brush` makes a new unfrozen brush on each call, and
  `ChangesView.cs:278-284` calls it per diff line (up to 2 MB of diff). Cache frozen brushes by hex. First grep that no caller changes a
  brush it got (a frozen brush throws on change); if one does, give that caller its own copy.
  *Why:* a large diff stalls the UI thread on allocations.
- [ ] **B6. The transcript view reads turn facts once per file.** `TranscriptView.cs:156-158` runs `TurnFacts.ReadFile` on every
  `ShowAsync`, including each effort-panel jump on the same file. Keep the last result by path + length + write time, as `_effortPath`
  (line 138) does for effort.
  *Why:* each click re-reads a transcript that can be 20 MB.
- [ ] **B7. One id rule.** `SessionWindow.Tabs.cs` (around line 362) compares session ids with `==`; the rest use
  `OrdinalIgnoreCase`. Make it match. Where the code cuts an id to 8 characters by hand, call `ClaudeCli.ShortIdOf`.
  *Why:* the same id must match the same way everywhere; one case-sensitive compare can miss a session.
- [ ] **B8. The log never throws and does not grow forever.** `AppLog.cs` catches only `IOException` (line 31) and never rotates. Catch
  every exception in `Write`; when the file passes 5 MB, move it to `app.log.1` (replacing the old one) and start a new one.
  *Why:* logging runs inside catch blocks; a throw there turns a handled error into a crash. The log is written every pass, for weeks.
