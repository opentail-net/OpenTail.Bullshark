## Decisions made while building

### Item 1 (built 2026-11-17)

- D1.1 Adoption ignores ended sessions. `SupervisorPolicy.Decide` adopts a listed session of the name only when its state is not `done`, `stopped` or `failed`. With the completed listing, a finished session of the same name would otherwise be adopted and never replaced, so the role would be silently dead. Cost: with no record, an idle `done` session of the same name now starts a second session, because the listing does not tell an idle `done` from a completed one. The owner may want to revisit this.
- D1.2 Listings. The pass lists with `--all` in the runner, the loop and the window. The window's refresh lists twice again: the active listing for the rail, `_agents` and the name checks, and the completed listing for the pass. This gives back the one `agents` call that review item 3 (AgentsOncePerPass) had saved, as the plan expects.
- D1.3 Stopped and failed alerts. `AlertKind.Stopped` and `AlertKind.Failed` are new. They are written to `LastAlert` as `Stopped: ...` and `Failed: ...`, once per entry into the state (via `LastState`), and never resume. `AttentionList` shows them under "Needs you" as the new `AttentionReason.Stopped` and `AttentionReason.Failed`, also for a listed session in that state, so no new UI is needed.
- D1.4 States checked on 2026-11-17 with `claude agents --json` and `--all` (counts only): the active listing holds `blocked`, `done`, and interactive `busy` and `idle`; `--all` adds 10 `done` and 2 `stopped`. `failed` has not been seen. It is handled as the string `failed`; to verify when one appears.
- D1.5 Owner decision, recorded only and not changed: should a `done` coder in a live run ever be woken? Today: no. Still open.
- D1.6 Tests: 13 new (policy 5, runner 2, CLI argument 1, loop 1, attention 4). Full suite 464 passed, 0 failed.

### Item 2 (built 2026-11-17)

- D2.1 The "no action" check sits inside the over-limit branch. The plan's wording on its own (no action whenever `LastAlert` starts with `RestartLoop:`) would also stop the resume that its own test expects once the restarts age out. So: over the limit with the alert standing, nothing; under the limit, a resume (which clears the alert, as the runner already does); over the limit with no alert yet, the alert.
- D2.2 A stale `RestartLoop` alert on a session that came back by itself does not affect anything while it is listed, since the listed branch does not read the alert. Known limit: if that session is lost again while over the limit, the old alert still stands, so no new alert is written. The owner still sees the standing alert under "Needs you".
- D2.3 Tests: policy 2 (one alert while the limit holds; a resume once the restarts age out), runner 1 (a loop alerts once, a resume clears it, and a second loop alerts again). Full suite 467 passed, 0 failed.

### Item 3 (built 2026-11-17)

- D3.1 Seam. `TranscriptIndex.Build(root, readFile)` is a new public overload; `Build(root)` passes `TranscriptReader.ReadFile`, so no caller changed. The Core project has no `InternalsVisibleTo`, so the reader has to be public for a test to inject it.
- D3.2 `Skipped` is an `IReadOnlyList<SkippedTranscript>` (the path and the error's message). It is always present, and empty when every file was read. The window logs one more line only when it is not empty.
- D3.3 Known limit, as the plan asks: messages a skipped file counted before its error stay in the shared ledger, so the totals can include part of a skipped file. The digests and the file list do not include it. Not fixed.
- D3.4 Only the per-file read is guarded, as the plan says. The folder listing itself is not changed.
- D3.5 Tests: 3 new (a file removed after listing; a file held with no sharing; an access-denied file). Full suite 470 passed, 0 failed. The whole solution builds; the one warning (`MainWindow.xaml.cs`, CS8601) was there before.

### Item 4 (built 2026-11-17)
