# Round 10 review (0b873e8..de06411), read-only. Nothing above MEDIUM; one MEDIUM of low confidence.

1. MEDIUM (confidence low-medium) TranscriptIndex.cs:109-124, 131-133 + ListFiles. The cache key (Length, LastWriteTimeUtc) comes from the FileInfo that EnumerateFiles returned, i.e. NTFS directory-entry metadata. For a file another process holds open for writing (a live Claude Code session) that metadata can lag the real file. Scenario: build 1 sees (L_dir, T_dir) but reads real content up to L_real; entry stored as (L_dir, T_dir). Later the session appends; if the directory entry is still stale at build 2, FromCache hits and the live session's digest (last text, turns, usage, totals) is stale until the metadata flushes. The old code always read the file. Fix: take the key from a fresh stat (File.GetAttributes-free: new FileInfo(path) / File.OpenHandle + RandomAccess.GetLength) at read time, and never use the cache for files written in the last ~2 minutes.
2. LOW (high) IndexCache.cs:181 and :159. Save catches only IOException/UnauthorizedAccess/NotSupported, but the doc says "nothing is thrown". JsonException/InvalidOperationException (e.g. System.Text.Json refuses a string with a lone surrogate) propagates out of TranscriptIndex.Build (line 126) and fails the whole history load, and the .tmp is not deleted. Load: line 155 `entry.Path.Length` throws NullReferenceException if the file has "path": null (or "files": null, line 153), which is not in the filter at 159. Fix: catch Exception in Save (delete temp) and in Load (return null).
3. LOW (high) IndexCache.cs:169-185, TranscriptIndex.cs:126. Save is not under FileLock (the other stores use FileLock.Hold + WriteAtomic) and the temp file is created with File.Create. Effects: two writers (window + bench, or two windows) each write a full snapshot and the last move wins, no corruption; a window of an older build and one of a newer build overwrite each other's cache on every start (ReaderId differs, line 150) so both lose the benefit; a crash between Create and Move leaves `transcript-index.json.<guid>.tmp` holding transcript text (first user text, last assistant text, recap) forever; nothing sweeps them. Fix: use FileLock.WriteAtomic (or Hold) and delete stale *.tmp beside the cache on Save.
4. LOW (high, rare) TranscriptIndex.cs:133. Same length + same write time is trusted. A restore that preserves mtime (robocopy /COPY:DAT, archive extract) or an in-place rewrite of equal size after a clock-preserving edit gives stale content with no way to notice. Transcripts are append-only so ordinary use is safe. Fix (optional): add a cheap hash of the last 4 KB to the entry.
5. LOW (high) HistorySearch.cs:86-103, 112-125. A batch is read in full (32 sessions) before results are taken in order, so after the 100th match up to 31 later sessions are read and thrown away; Parallel.For has no MaxDegreeOfParallelism, so a search takes every core on a pool thread beside the UI (same for Build at TranscriptIndex.cs:83, 102). Results, unreadable count and stop at MaxResults are still exactly the sequential ones (errors after the stop are not counted, line 100-101). Fix: MaxDegreeOfParallelism = Environment.ProcessorCount - 1 and pass the token to Parallel.For.
6. LOW (medium) TranscriptIndex.cs:83-85, 96-126. Memory peak: reads[] keeps every file's own ledger (messages duplicated across resumed files) plus the Combine ledger plus, on cache path, the loaded Document, the Restore ledgers, and a second DTO copy in Save (`entries.ToList()`, EntryOf). Roughly 3x the old single-ledger footprint for the message keys; fine for thousands of files, noticeable for hundreds of thousands of messages. Fix: not needed now; drop reads[i].Ledger after Combine consumed it.
7. LOW (high, latent) IndexCache.cs SummaryDto/Restore. The DTO omits TranscriptSummary.FileLastWrites, LatestCwd, FileFolders (and Records is 0). DigestOf uses none of them today, so cached == read for the index. If a later round adds one of them to SessionDigest, cached sessions silently lose it (ReaderId would not change the meaning, only the code). Fix: a test that compares every TranscriptSummary property used by DigestOf, or note it next to DigestOf.

## Judged correct
- Dedupe across files (TranscriptIndex.cs:140-168, UsageLedger.cs:18-23, 36-42): per-file ledgers hold the per-file max per key; Combine records pairs in file order, so the first file keeps Model and FirstFile, usage is the max over files (Max is associative), and Total/ByModel/Count equal the sequential ledger. The per-file UsageByModel uses `first` = this file's own values for keys no earlier file counted, which equals ByFile at the end of that file's read in the sequential build. Partial ledgers of unreadable files stay counted; a non-IO error is rethrown in listing order.
- Order independence: cache entries are per file and the order comes from the live listing, so changed creation times only change attribution as before.
- Cache invalidation: entries for deleted/renamed files drop out (entries built from reads only; Save runs when count differs or any file was read); different ReaderId (module MVID) gives null; a damaged entry falls back to reading (catch at 138); writes are temp + move overwrite, so a reader sees the old or the new file; Move failing because another process has it open is caught (IOException/UnauthorizedAccess). UTC ticks, no timezone/DST issue. A file that grew between enumeration and read is re-read next time (recorded length is the older one).
- RawProbe (HistorySearch.cs:152-166, 178-186): a probe is a run of characters no JSON writer escapes, contiguous in word and text, so it is contiguous verbatim in the raw line of the same message; \uXXXX of non-ASCII or "\/" cannot remove it (such characters are not "safe", they split runs). Words with no safe char get empty probe, which disables the filter for that word. Only "you"/"claude" kinds are searched and their text is verbatim message text. Case-insensitive on both sides.
- Parallel search: results written by index, consumed in order; cancellation is captured as the error and rethrown in order (line 97), plus the token check each line; extraText is run on pool threads but reads the immutable `marks` snapshot (SessionWindow.Search.cs:110, SessionWindow.Library.cs:151) so it is thread-safe.
