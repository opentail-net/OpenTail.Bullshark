## Decisions made while building
### Item 1 (file overlap)

- D1.1 Built from the transcripts, not from the index. The digests carry no write times, so `TranscriptReader` now also records the last write time of each file (`TranscriptSummary.FileLastWrites`, an optional field added at the end). `SessionWritesCache` reads a transcript again only when its length or last write time changed, because a pass runs every 15 seconds.
- D1.2 The signature is `Find(run, records, writes)`, not `Find(run, digests)`. A `RunRecord` holds no session ids, so the state records map each spec name to its session. Only the sessions of the run count.
- D1.3 A relative path is taken from the run's folder. Paths compare without case on Windows only (`C:\A.cs` and `c:/a.cs` are one file); elsewhere they compare exactly.
- D1.4 One Overlap item per session per shared file. `Gained` announces each (session, file) once. A session that already waits for another reason is still announced for a new shared file. A session whose reason changes from a shared file to another reason is not new, as before.
- D1.5 Needs you shows each session once, with its first reason, and the count is distinct sessions. The Changes tab lists the shared files above its lists.
- D1.6 Not built: the rule to skip sessions in their own worktree. No session has a worktree (additions item 3 is skipped), so there is nothing to skip. The box is left open.
- D1.7 Limit: a subagent's transcript (under `subagents/`) has its own session id, so its writes are not seen as writes of the coder that started it.
- D1.8 Verified: 19 new Core tests (`FileOverlapTests`, `OverlapAttentionTests`), 492 passing in all. The solution builds with App. The rail mark, the Needs you row and the Changes list were not run in a window.

### Item 2 (merge check)

- D2.1 `merge-tree` runs with `-z`. Checked on git 2.53 in a scratch repository: the plain output quotes a name with a non-ASCII character (`"d\303\251.txt"`), while `-z` gives the exact name, and its file list ends at an empty field. Exit 0 is clean. Exit 1 with a tree id and a file list is a conflict. Exit 1 without a tree id (a missing ref, an unborn HEAD) is a problem, not a list of conflicts.
- D2.2 The plan says "read-only", which is not exact. `merge-tree --write-tree` writes the merged tree as objects into the object database. These are unreferenced, and git removes them in a later garbage collection. It moves no ref, and it does not touch the index or the working tree. The doc comment of `MergeCheck` says this.
- D2.3 The default branch is looked up in this order: `origin/HEAD` (the full ref it points to, for example `refs/remotes/origin/main`), then the local `main`, then `master`. A repository with none of them gives "no default branch".
- D2.4 The trigger reads the listing with completed sessions, so a coder that is `done` is seen. Each entry into `done` starts one check on a pool thread. A coder that leaves `done` loses its result and is checked again on its next entry. The result shows on the next pass (at most 15 seconds later), not at once: the pass already redraws the rail.
- D2.5 A coder whose folder is not known yet is not checked; it is tried again on the next pass.
- D2.6 "Copy resolve prompt" is in the session's Changes tab, shown only when its check found conflicts. The Changes tab already has the session's folder and file list. The prompt names the branch and the files, asks the coder to merge, resolve, test and commit, and says "Do not push".
- D2.7 A conflict is a notice, like an overlap: it is announced when it joins the list, even when the session already waits for another reason. `Gained` now treats both notice reasons this way (a session that changes from one reason to another is still not new).
- D2.8 Not verified in a window: the ⚠ mark, the Needs you row, the Changes tab button, the clipboard. The check itself is tested with a fake git (20 new Core tests in all for this item, in `MergeCheckTests` and `ConflictAttentionTests`), and it was run once by hand on a scratch repository for the output shapes.

### Item 4 (where the effort went)

- D4.1 One pass over the transcript lines (`EffortReport.From`). Turn boundaries follow `TurnFacts`: a typed prompt starts a turn, `turn_duration` ends it, and a turn still open at the end of the file ends there. A test checks that the turn count is the same as `TurnFacts` on the same lines.
- D4.2 Thresholds, as the plan says: a file is listed when it was read more than 3 times, a command when it was run more than 2 times (exact text). A failed call is counted once per call id, under its tool's name. The first line of each item is where the view jumps.
- D4.3 Tokens are input, output and cache writes. Cache reads are left out, because they re-read context that was already paid for; the panel's tooltip says so. Usage counts once per message (id and request id), as the usage ledger does. Usage before the first prompt is in no turn, so it is not in the panel.
- D4.4 A turn "with no output" wrote no file (Write, Edit, MultiEdit or NotebookEdit) and has no text block that is not blank. A turn still running in a live session is judged as it stands when it is read.
- D4.5 The panel is read once for each transcript when it is shown, on a pool thread. A jump to a line does not read it again, and it does not refresh while the transcript stays open: the owner opens the session again to see later work.
- D4.6 Not verified in a window: the panel's layout and the jump. The jump reuses the focus-line path that search uses.
- D4.7 The panel's colours are set when it is drawn, so a theme change while it is open does not repaint it.
- Verified: 8 new Core tests (`EffortReportTests`); 520 passing in all; the solution builds with App.

### Item 5 (start a run later)

- D5.1 The skip is in the spec list a pass receives (`RunStore.DueSpecsOf`), not inside `SupervisorPolicy`. A waiting run has no spec in the pass, so the policy never sees it, and nothing is started or adopted. A test shows that a waiting run makes no `claude` call and writes no file.
- D5.2 WPF has no time picker, and a package would be needed, so the setup page has a text box that takes a 24-hour `HH:mm` on this computer's clock. The start is the next time the clock shows that: today if it is still ahead, otherwise tomorrow.
- D5.3 A text that is not a time stops the Start press before anything is written, and the reason goes to the status line.
- D5.4 A waiting run shows under its folder as "Run xxxx starts at HH:mm". Right-clicking it and choosing "Start now" clears its time in runs.json, then runs a pass. The folder of a waiting run is checked for trust only when the run is due, because the trust step is part of the pass.
- D5.5 The time is kept in runs.json as an optional field. A file without it loads as "start at once". Only the window starts runs, so a time that passes while the window is closed takes effect at the first pass after the window opens. The setup page says "Starts only while this window is open."
- D5.6 Built 2026-11-18: "Start when my usage limit resets", with the reset time read from the transcripts. The decisions are in `limit-reset-start-2026-11-18.md`.
- D5.7 Not verified in a window: the setup box, the waiting row and its menu.
- Verified: 17 new Core tests (`DelayedRunTests` 7, `StartTimeTests` 10); 537 passing in all; the solution builds with App.

### Item 6 (storage view and archive)

- D6.1 The archive moves each file to the same relative place under `bullshark-archive` (project folder and file name kept), so Restore puts it back at its own path. A file of the same name already in the archive, or already back in place, is refused, and nothing is overwritten.
- D6.2 A session is protected when its id is in the full listing (`agents --json --all`) or in the state records. The archive compares the file name, which is the session id, against that set, and refuses the file with the reason.
- D6.3 The page offers only the session transcripts directly in a project folder. Subagent files stay with their session. The report counts every `.jsonl` file under the folder, subagent files included, and says so in its name.
- D6.4 `bullshark-archive` sits outside `projects`, so Claude and the history index do not read it. After an archive or a restore the window reloads History, so the archived sessions leave the list.
- D6.5 Known limit: the subagent folder of an archived session stays under `projects`, because only the session file is moved. It is small, and nothing reads it as a session.
- D6.6 The confirm box is a standard Yes/No message box that lists the file names. Restores are not asked about, since a restore is reversed by archiving again.
- D6.7 Not verified in a window: the page, its checkboxes, the confirm box, the History reload. The tests move files only in temp folders. No real transcript under `~/.claude` was moved, and no file was deleted.
- D6.8 Verified: 9 new Core tests (`StorageTests`); 546 passing in all; the solution builds with App.
