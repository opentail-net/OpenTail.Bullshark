1. HIGH, confirmed. SupervisorPolicy.cs DecideSession end (`return []`, ~line 205) + DaemonStatus.cs IdleListing (~line 66) + SupervisorRunner.cs:82,132. A listed working/blocked session while the daemon is "not running" becomes state "stale". Policy has no branch for it: it is listed so not "gone" (no Resume), not blocked (no alert), returns []. Real not-running output shows roster.json "updated 6604s ago", so the listing can keep a dead "working" row for hours. Scenario: reboot/daemon crash, roster still says working: the role is never resumed, only the Needs-you note shows. It stays so until the roster drops the row (then Resume) or the owner acts. Same root in the Adopt branch (SupervisorPolicy.cs ~150): lost record + a stale-listed same-name session is adopted with State "stale" and the role is never started. Fix: treat state "stale" as lost in DecideSession (Resume under restart-loop rules, not when reached/stopped) or raise one alert per entry; do not adopt stale rows.

## Judged correct
- Daemon "not running" never blocks a pass; Unknown (timeout, exception, unrecognised text) returns the listing unchanged (ClaudeCli.DaemonStatusAsync catches all but cancellation; exit code ignored).
- NotRunning is tested before Running; "unreachable" before "reachable".
- IdleListing is idempotent (window and runner both apply it) and leaves done/stopped/failed rows alone.
- Stop/failure alert cleared only when the session is seen listed in another state; WasStoppedOrFailed prefers LastState.
- Limit notices: RankOf, told level = highest of the run's records, quiet lowering, LimitLevelSet(null) when no limit, and LimitReached no longer overwriting LastAlert are consistent.
- LimitItem needs listed and not done; Gained now remembers overlaps and conflicts.
- Budgets read before the pass (ForRuns); ElapsedOf gives zero for no started session or a future StartAt.
- SessionWritesCache head hash and trailing whole-JSON-line handling re-read from the same offset, so the ledger counts once.
- New CLI/IO work (daemon status, version, transcript facts, retention read) runs on pool threads; UI-thread additions are trivial.
