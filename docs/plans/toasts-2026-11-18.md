# Windows toast notifications, minimalist, 2026-11-18

Owner decision (2026-11-18): CommunityToolkit is OK; keep it **minimalist**; sound only **a little ding / ping**.
Why: flash and sound only reach the owner while the window is on screen; a toast reaches them when it is minimised or behind other apps.
Nothing is ever sent to a session (principle 3). This plan adds the one new package the owner approved.

## What exists (read first)

- `SessionWindow.Attention.cs` `AnnounceAttention()`: runs after every pass; new items (`AttentionList.Gained`) and escalation re-alerts (`_escalation.Update`, see `escalation-2026-11-18.md`) call `SystemSounds.Asterisk.Play()` and `TaskbarFlash.UntilFocused(handle)`, unless ui.json `notify` is false (`AttentionList.NotificationsOn`).
- `UiFile.Read/Set` for ui.json settings. `AppLog.Write` for logging.
- `src/OpenTail.Bullshark.App/OpenTail.Bullshark.App.csproj`: `net10.0-windows`, one package (`WPF-UI.Terminal`).

## Contracts this must satisfy

| Member | Promise |
|---|---|
| `AnnounceAttention` | Existing sound and flash behave exactly as now. A toast is added next to them, only when something sounds. `notify:false` silences toasts too. |
| Sound | The ding stays the existing `SystemSounds.Asterisk` played by the window. The toast itself is **silent** (`<audio silent="true"/>`) so there is one ding, not two. |
| Principle 3 | A toast has no buttons that act on a session. Clicking it only brings the window to the front (and selects the session's tab if that is simple; otherwise just the window). |
| Privacy | Text = session name and reason only (e.g. "ovc-coder · blocked"). No prompt text, no file contents, no paths. |
| Package | The only new package: `CommunityToolkit.WinUI.Notifications` (check on nuget.org: its licence must be MIT or compatible and the version current and not pre-release; write both in the plan). If it needs a Windows-versioned target framework (e.g. `net10.0-windows10.0.19041.0`), change the App's `TargetFramework` and confirm the whole solution still builds and tests pass; report it. |
| Failure | A toast that cannot be shown (unsupported OS, focus assist, any exception) is logged once and never throws into the pass. |

## Design decisions (AFK; change if you disagree)

- D1 Minimalist: one toast per announcement batch (not one per session): title "Needs you", body the first session name and reason, plus "and N more" when there are more. Re-alert: title "Still waiting", same body style. Nothing else (no image, no buttons, no progress).
- D2 Only when the window is NOT the active window (`IsActive` false) or is minimised. When it is in front, the flash and ding are enough.
- D3 Setting in ui.json: `toast` (bool, default true); `notify:false` overrides everything. A tiny Core helper `ToastText.Build(gained, due)` returns title and body (pure, tested). The palette gets one action "Toggle toasts" next to "Toggle sound and flash" (follow how that action is done).
- D4 Toast `tag`/`group` set to a fixed value so a newer toast replaces the older one in the action centre instead of stacking (HA notification tag pattern).
- D5 Clicking the toast: activates the window (`Activate()`, restore from minimised). Handling the activation callback from an unpackaged app: use the library's `ToastNotificationManagerCompat.OnActivated`; keep it to "show window". If the callback is unreliable without a Start-menu shortcut, say so and keep toasts without click handling (the library registers a COM activator for unpackaged apps; read its docs first).
