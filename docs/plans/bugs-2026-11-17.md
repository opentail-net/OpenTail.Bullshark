## Items

### 1. Do not resume sessions that finished or were stopped
Now: the pass lists without `--all`, so a finished or stopped session is absent, and the policy resumes it as lost (with the "You were restarted" prompt). Only Bullshark's own close-tab stop removes the spec first.

- [ ] `ClaudeCli.ListAgentsAsync(bool includeCompleted, CancellationToken ct = default)` adds `--all`; the old signature stays and means `false`.
- [ ] The supervisor pass uses `includeCompleted: true`: `SupervisorRunner.CheckOnceAsync(specs, ct)` and `SupervisorLoop.RunPassAsync(specs, ct)` list with it, and the window's background step lists twice — the default list for `_agents` (display, unchanged) and the `--all` list for the pass. This gives back one CLI call that review item 3 saved; record that in "Decisions".
- [ ] `ResolveSessionIdAsync` keeps the default listing (a just-started session is active).
- [ ] Policy, with the full list:

| Listed state | Action |
|---|---|
| not listed at all | as today: resume, or `RestartLoop` alert |
| `stopped` | new alert `Stopped` once per entry (via `LastState`), never resume |
| `failed` (Agent View state, not yet seen here) | new alert `Failed` once per entry, never resume |
| `done` | nothing (as today) |
| `blocked` | as today |
| anything else | nothing (as today) |

- [ ] Rail/status show the new alerts like the existing ones (text from `LastAlert`); no new UI.
- [ ] Tests: each row; a `done` session present only in the `--all` list is not resumed; the default `ListAgentsAsync()` argument list is unchanged.
- [ ] Owner decision, record only: should a `done` coder in a live run ever be woken? Today: no.

### 2. `RestartLoop` alerts once, not every pass
Now: while a session is not listed and over the limit, every 15 s pass logs `ALERT RestartLoop`.

- [ ] Policy: if `record.LastAlert` starts with `RestartLoop:`, return no action.
- [x] Runner: a `Resume` that succeeds clears `LastAlert`, so a later loop alerts again. (Already built on `additions-phase-a`, f7e60e3, decision D1.3.)
- [ ] Tests: two passes over the limit give one alert; after the restarts age out, a resume happens and clears it; a second loop alerts again.

### 3. One bad transcript does not break the history
Now: `TranscriptIndex.Build` reads each file with no per-file guard; a file deleted after listing (Claude's cleanup) or locked makes the whole history load fail.

- [ ] Catch `IOException` and `UnauthorizedAccessException` per file (includes `FileNotFoundException`), skip it, and report skipped files in the result (new optional `Skipped` list on the index result) so the window can log the count.
- [ ] Known limit, record it: messages read before the error stay counted in the ledger.
- [ ] Tests: a file deleted between listing and reading (inject the file list or the reader), an unreadable file; the other files still come back.

### 4. Open transcripts the same way everywhere
Now: `CacheReport` and `TranscriptTail` open with `FileShare.ReadWrite | FileShare.Delete`; `TranscriptPager` (`File.OpenRead`), `TranscriptReader.ReadFile`, `TurnFacts.ReadFile` and `HistorySearch` (`File.ReadLines`) do not, and can throw while Claude writes.

- [ ] Core helper `TranscriptFile.Open(path)` (read, share ReadWrite|Delete) and `TranscriptFile.ReadLines(path)` (lazy, UTF-8, same sharing).
- [ ] Use it in the four places above and in `CacheReport`/`TranscriptTail`.
- [ ] Test: a file held open for writing by the test can still be read and paged.
