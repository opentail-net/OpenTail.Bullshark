- `run` and `-c` (for the first and last sessions) depend on the server's list; whether that list is limited to the folder is not yet read. Exit codes of `run` are not read.

## 3. Data and config location

VERIFIED from the code (exe:1069753-1069760, 481438-481445, 705577-705816, 467050, 489810-489813, 994721):
- Without XDG variables, on Windows: data `%USERPROFILE%\.local\share\opencode`, config `%USERPROFILE%\.config\opencode`, state and cache under `.local\state` and `.cache`.
- The data folder holds `opencode.db` (the sessions), `auth.json` (credentials) and `log\`. The owner's real folder is the one under `%USERPROFILE%`. **Its database is not opened by this research.**
- `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` move the base folders. **For scratch probes, set all four.**
- `OPENCODE_DB` moves the database; an absolute path or `:memory:` is used as-is. Caveat (exe:994721): the first-run migration check tests the owner's `opencode.db` regardless of `OPENCODE_DB`, so `XDG_DATA_HOME` must also be set.
- `OPENCODE_TEST_HOME` does **not** move data or config (exe:1069783-1069785).
- Config files read: `config.json`, `opencode.json`, `opencode.jsonc`; overrides `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_DISABLE_PROJECT_CONFIG`.

## 4. Sign-in and quota

- Providers are set up with `/connect` (an API key, or a provider login such as a ChatGPT Plus/Pro plan or a GitHub Copilot device login). Credentials sit in `auth.json` and a local credential store. VERIFIED from the provider docs as summarised; not opened.
- A ChatGPT Plus or Pro login: usage counts against the plan (docs, VERIFIED as summarised).
- `opencode run` billing: the docs are silent. ASSUMED: it uses the connected credential, so an API key is billed per token and a plan login draws on the plan. **A summary call is therefore a real cost for the owner. The cost must be shown before the call, as the other providers do.**

## 5. Server mode and HTTP API (installed 1.4.3)

Source: the server's routes and options in `opencode-windows-x64\bin\opencode.exe` (read as text, not run). `exe:N` is the line of that file. Docs read through a fetch.

**Version skew (VERIFIED).** The installed 1.4.3 registers `/session`, `/event` and `/doc`, with no `/api` prefix. The public docs describe `/api/session`, `/api/event` and `/docs/openapi.json`, which match a newer release. **The app must use the paths of the installed build and read its version at setup.**

| Method | Path | Purpose | Read-only | Source |
|---|---|---|---|---|
| GET | `/session` | List. Query: `directory`, `roots`, `start`, `search`, `limit`. Fields used: `id`, `title`, `directory`, `parentID`, `time.created`, `time.updated`, `time.archived` | yes | exe:803943; schema exe:704343-704388 |
| GET | `/session/:sessionID` | One session | yes | exe:~803990 |
| GET | `/session/:sessionID/message` | Messages. Query: `limit`, `before` (needs `limit`). Each: `info` (id, sessionID, role user or assistant, time.created) and `parts` (type, text) | yes | exe:804322; exe:590071-590394 |
| GET | `/event` | Server-sent events. First frame `server.connected`, a heartbeat every 10 seconds, then bus events. Event names verified: session created, updated, deleted; message updated, removed; message part updated, removed. Payload shape ASSUMED | yes | exe:806504 |
| GET | `/doc` | OpenAPI 3.1 document for the installed build | yes | exe:811382 |

**Starting the server (VERIFIED from code, not run).**
- `opencode serve` starts a headless server and blocks until it is stopped (exe:936917-936931).
- Flags: `--port` (default 0), `--hostname` (default 127.0.0.1), `--mdns`, `--cors`. The config keys `server.port`, `server.hostname`, `server.mdns` and `server.cors` are read, and an explicit flag wins (exe:936867-936913).
- Port 0 means it tries 4096 first, then an OS-chosen port (exe:811484). The server prints `opencode server listening on http://<hostname>:<port>` on stdout (exe:936927). The app reads the port from that line.
- **Authentication:** HTTP Basic. The user is `OPENCODE_SERVER_USERNAME` (default `opencode`) and the password is `OPENCODE_SERVER_PASSWORD`. If no password is set, the server runs without authentication and warns (exe:811293-811300, 936922). A failed login returns 401 (exe:751620). **The app would set a random password for each start.**
- The directory for a request is the `directory` query, else the `x-opencode-directory` header, else the server's working folder (exe:806940).
- The npm wrapper starts the native x64 binary, or the baseline one on a CPU without AVX2 (VERIFIED). Only the x64 binary was read.

**Listing without a server (VERIFIED from code, not run).** `opencode session list --format json` lists the sessions of the working folder, with `id`, `title`, `updated`, `created`, `projectId` and `directory` (exe:993860-993930). No server is needed for the list. **Messages need the server or the database.**

**Newer docs (fetched, not 1.4.3).** `GET /api/session` takes `limit`, `order`, `search`, `parentID`, `archived`, `directory`, `project`, `subpath` and `cursor`. `GET /api/session/{id}/message` takes `limit`, `order`, `cursor` and `type`. The newer spec is OpenAPI 3.1.0 titled "opencode HttpApi" (version 0.0.1), and it authenticates with a session token rather than Basic. Not usable with 1.4.3.

**Not found or unverified:** the payload shape of the session and message events; which command calls the worker's server routine; the rest of the docs; the baseline binary.

## 6. Database schema

**Installed build (v1, VERIFIED from the embedded code of 1.4.3, exe line numbers):**

| Table | Key columns | Meaning | Source |
|---|---|---|---|
| `session` | `id` (key), `project_id`, `parent_id`, `slug`, `directory`, `title` (not null), `version`, `workspace_id`, `time_created`, `time_updated`, `time_archived`, `time_compacting` | one chat; `directory` is its folder | DDL 489945-489968; row map 704301-704320 |
| `message` | `id`, `session_id`, `time_created`, `time_updated`, `data` (JSON) | the role is `data.role`: user or assistant | DDL 489969-489974; insert 810651-810660 |
| `part` | `id`, `message_id`, `session_id`, `time_created`, `time_updated`, `data` (JSON) | a text part has `data.type` "text" and `data.text` | DDL 489975-489984; insert 810673-810682; TextPart 590071-590073 |
| `project` | `id`, `worktree` (the project folder), `name`, `vcs` | the project root | 489925-489936 |

- **No version number** in the database. The migrations are tracked in a Drizzle table, `__drizzle_migrations` (488835-488847); 10 bundled migrations, the last `20260323234822_events` (489846).
- **Times** are integer milliseconds since the epoch (489915-489916, 704315-704316).
- **Data folder (VERIFIED):** `$XDG_DATA_HOME/opencode`, else `%USERPROFILE%\.local\share\opencode`, with no Windows AppData branch (xdg-basedir 467113; Global 481442). The database is `opencode.db` on the "latest" channel (484317, 489803-489815). `OPENCODE_DB` moves it (an absolute path or `:memory:` is used as-is; 489810-489813). `OPENCODE_DISABLE_CHANNEL_DB` forces `opencode.db` (467051). `OPENCODE_SKIP_MIGRATIONS` skips the migration SQL (489852). No `OPENCODE_DATA…` variable exists in either build.

**Newer build (v2, fetch-summary, not verified from source):** the sessions move to `session_v2`, the messages to `session_message` (with a `type` of user, assistant, synthetic or system), and the parts to `session_part` (a composite key). Many new tables. A migration table named `migration`. A v1 database is migrated into v2 on first run of the newer build, and the newer build also reads `data/opencode-next.db` if present. **So a v1 and a v2 database look different, and the app must check which one it is reading.**

**Unverified:** the verbatim v2 table definitions; whether the v2 database file is also called `opencode.db` (ASSUMED yes).

**The owner's database (checked on a scratch copy, names and row counts only; the copy was taken with the database's log files):** it has the v1 tables and the v2 tables together. The v1 tables hold 131 sessions, 276 messages and 186 parts; the v2 `session_message` table is empty; a `migration` table records 38 applied migrations, so a newer build has opened this database. The table `session_v2` is absent. **So "refuse a database with v2 tables" would refuse the owner's own database.** The rule must be decided by the plan: read the v1 tables that the installed build reads, and say which build wrote the latest data. Which build the owner uses day to day is an owner question.

**Implication for the route (not yet decided):** the installed build's tables can be read in read-only mode, with the JSON in `data`. The reads would show what the installed build sees, which may be older than what a newer build wrote.
